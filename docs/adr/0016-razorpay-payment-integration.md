# ADR-0016: Payment keyed to Checkout not Order, dual signature paths with the webhook authoritative, fetch() over the Razorpay SDK

## Status
Accepted

## Context
Phase 8 closes the loop [ADR-0013](0013-commerce-money-math.md) deliberately left open: order creation (Phase 5) produces a `PLACED` order with no live payment-gateway integration behind it. The brief requires create-order/checkout/verification/webhook/signature-verification/idempotency/failure-handling/refund, with the hard constraint that "only verified server-side payment events may finalize payment state." Three implementation questions needed resolving:

1. **`payments.order_id` in the original spec ([database-tables.md](../database-tables.md) §4) is singular**, but Phase 5's checkout already splits a multi-vendor cart into multiple `Order` rows under one `Checkout` ([ADR-0013](0013-commerce-money-math.md)). A literal one-payment-per-order design would force a customer through a separate Razorpay checkout per vendor in their cart — a materially worse experience than the single-checkout flow Phase 5 already built, and nothing in the brief asks for that.
2. **Razorpay's checkout.js gives the browser a `razorpay_payment_id`/`razorpay_order_id`/`razorpay_signature` triple on success**, which the brief's "never trust frontend payment success" principle correctly refuses to accept at face value — but the signature itself is an HMAC-SHA256 the browser cannot forge (it's computed server-side by Razorpay using a secret only Razorpay and this app hold), so *verifying* it server-side is not "trusting the frontend," it's trusting cryptography. The question is whether that verified callback alone is allowed to finalize payment, or whether only the asynchronous webhook may.
3. **The official `razorpay` npm SDK** wraps a handful of REST calls (`orders.create`, `payments.fetch`, `refunds.create`) that are individually simple, and this codebase has a consistent pattern (Phase 4-7) of reaching for Node's built-in `crypto`/`fetch` over adding a dependency when the primitive is this small.

## Decision
1. **`Payment.checkoutId` replaces the spec's `order_id`.** One Razorpay order = one `Payment` row = the sum of every `Order.grandTotal` under that checkout. A successful capture marks every order under the checkout `PAID` in one pass (`payment-service.ts`'s `markCheckoutOrdersPaid()`); a refund targets the same set. `purpose = 'ORDER'` is the only purpose this phase actually drives (wallet top-up/e-pin/subscription purchase remain designed-but-not-wired payment purposes, per the original spec's column, same "modeled, not all paths built" discipline as every prior phase).
2. **Both the checkout.js callback and the webhook are accepted, but the webhook is authoritative and either path is idempotent against the other.** The callback's signature is verified (HMAC-SHA256 of `order_id|payment_id` with `RAZORPAY_KEY_SECRET`) and, if valid, finalizes the payment immediately — this is a legitimate, Razorpay-documented synchronous confirmation path, not "trusting the frontend." The webhook (HMAC-SHA256 of the raw request body with `RAZORPAY_WEBHOOK_SECRET`, delivered server-to-server, immune to a closed browser tab or a dropped callback request) is the resilient path that eventually confirms every payment regardless of what the browser did. Both paths funnel through the same `capturePayment()` function, which treats "already `CAPTURED`" as a successful no-op (the conditional-update idempotency pattern from [ADR-0015](0015-wallet-epin-subscription.md)) — so whichever arrives first wins and the second changes nothing. An *invalid* signature on either path is logged and rejected; it never finalizes anything, closing the "never trust frontend success" requirement at the cryptographic layer rather than a trust-the-caller one.
3. **`createRazorpayOrder()`/`verifyRefund()`/`initiateRefund()` call Razorpay's REST API directly via `fetch()` with HTTP Basic Auth (`key_id:key_secret`)**, not the `razorpay` SDK — three endpoints, no SDK-specific behavior this codebase needs, and it keeps the same "built-in primitives over a new dependency" discipline already applied to OTP/wallet-PIN/e-pin hashing. When Razorpay credentials are absent (this environment's placeholder-only `.env.local`, same as every other external integration in this project), `razorpay-client.ts` falls back to a clearly-logged, clearly-prefixed synthetic order id — the same dev-fallback pattern already established for MSG91/Resend (Phase 4) — so the full flow is exercisable without live credentials, and nothing here is silently treated as a successful real payment.

## Consequences
- A refund (full, this phase — partial refund amounts are schema-ready via `PaymentTransaction.amount` but not exposed in the admin UI yet) moves `Payment` to `REFUNDED`, moves every order under the checkout to `REFUNDED` via `transitionOrderStatusBySystem()` ([order-service.ts](../../src/server/domain/commerce/order-service.ts)), which — already, for free — triggers Phase 6's commission reversal and Phase 7's wallet claw-back. No new reversal logic was needed for this phase; it composes on what already exists.
- `order-state-machine.ts`'s `PAID -> REFUNDED` and `COMPLETED -> REFUNDED` rules gain `SYSTEM` as an allowed actor (previously `ADMIN`/`FINANCE` only), since the actual status flip is applied by the verified payment-service callback/webhook after an admin *initiates* the refund call, not by the admin's session directly — the same split already established for `PLACED -> PAID`.
- `payment_events` remains exactly as specified (append-only, `(provider, event_id)` unique) and is the evidentiary record for "every signature check this system ever performed, valid or not" — including rejected/invalid signatures, which are inserted with `signatureValid = false` rather than silently dropped, so an audit can distinguish "we never got this event" from "we got it and correctly refused it."

## Alternatives considered
- **Webhook-only, ignore the checkout.js callback** — rejected: materially worse UX (the customer's success page would have to poll rather than confirm immediately), and the callback's signature is independently verifiable, so there's no security reason to discard it.
- **Trust the checkout.js callback alone, skip the webhook** — rejected: the brief explicitly requires a webhook endpoint, and relying solely on a redirect/JS callback is fragile against a closed tab, a network blip, or a user who never returns to the success page after paying.
- **The `razorpay` npm SDK** — rejected for the reason in Decision 3; revisit if a future phase needs enough additional Razorpay surface (e.g. subscriptions-as-a-gateway-feature, route/marketplace payments) that reimplementing it via `fetch()` stops being the smaller amount of code.
