# ADR-0014: Commission engine — mutable lifecycle status on an immutable financial record, order-level calculation base, rule versions as rows

## Status
Accepted

## Context
Phase 6 builds the referral/commission engine against the decisions already recorded in [business-rules.md](../business-rules.md) Q-01–Q-07: unlimited-depth referral tree but only configured levels pay out (Q-01), no default commission rate — fully configurable per level/basis/kind (Q-02), an extensible qualifying-event list (Q-03), an eligibility predicate evaluated at commission-creation time (Q-04), referrer locked at signup with `SUPER_ADMIN`-only repoint (Q-05, already implemented in Phase 4), `PENDING` until order `COMPLETED` plus a configurable release window (Q-06), and full reversal via an offsetting record on refund/cancel, wallet balance never going negative (Q-07 — though the wallet itself is a later phase; see below). The Phase 6 brief additionally specifies a five-state lifecycle (`PENDING → ELIGIBLE → AVAILABLE`, with `REVERSED`/`CANCELLED` as reversal/dead-end states) and requires every commission record be immutable and reference order, order item (where applicable), beneficiary, level, rule version, calculation base, calculated amount, and status.

Three implementation questions needed resolving that the Phase 0 docs didn't fully pin down:

1. **[ADR-0002](0002-money-representation.md) names `commission_ledger` explicitly as one of the insert-only ledger tables** ("corrections are new, offsetting rows"). Taken completely literally, a five-state lifecycle would mean inserting a new row for every status change, which pushes "what is this commission's status right now" into an event-sourcing read model (latest row per logical commission) — materially more complex than the pattern Phase 5 already established and tested for `Order.status` (a mutable status column + a separate append-only history table), for no correctness gain in this phase (no wallet balance is yet derived from a sum-of-rows read, since the wallet itself isn't built).
2. **A Phase 5 order can contain items of more than one catalog kind** (a cart groups by vendor, not by kind), but `commission_rules.applies_to` is per-kind. The calculation base for a percent-of-order/percent-of-vendor-sale rule needs a precise definition when an order is mixed.
3. **`commission_rules` is "versioned via `effective_to`, never deleted"** per the original spec — i.e., changing a rate creates a new row and closes out the old one, rather than editing a rate in place. The brief asks every commission to reference "rule version."

## Decision
1. **`Commission.status` is a mutable column; every other field on the row (order, order item, beneficiary, level, rule, calculation basis, calculation base amount, calculated amount) is set once at creation and never updated.** Every status transition is also written to an append-only `CommissionStatusHistory` row (`commissionId`, `fromStatus`, `toStatus`, `actorId`, `reason`, `createdAt`) — the exact pattern `Order`/`OrderStatusHistory` already uses and that Phase 5's tests already validated. This is "immutable" in the sense the brief cares about (the *financial facts* — what was earned, from what, at what rate — can never be altered after the fact) without taking on an event-sourced read model for a value (current balance) nothing yet consumes. If a future wallet phase needs to derive a balance from ledger rows, it reads `Commission.amount` grouped by current `status`, which this design already supports directly.
2. **Calculation base is resolved per matching catalog kind, not per whole order.** Order items are grouped by `itemType`; a rule with `appliesTo = PRODUCT` uses the sum of that order's `PRODUCT`-kind items' `lineTotal` as its base for `PERCENT_OF_ORDER`/`PERCENT_OF_VENDOR_SALE` (which are the same number in this architecture, since Phase 5 already splits checkout into one `Order` per vendor — "order value" and "vendor sale value" are definitionally identical here). `PERCENT_OF_PLATFORM_FEE` uses the whole order's `platformFeeTotal` (fee isn't computed per-kind). `FIXED` ignores the base entirely. A single-kind order (the common case) behaves exactly as the naive "whole order" model would.
3. **"Rule version" is the specific `CommissionRule` row** (`Commission.ruleId`), not a separate version-number column. Activating a new rate is a transaction that closes the currently-active row (`effectiveTo = now()`) and inserts a new one (`effectiveFrom = now()`, `effectiveTo = null`) — the row's own identity and `effectiveFrom` timestamp already are the version, so a commission referencing `ruleId` is unambiguously pinned to the exact configuration that produced it, with no redundant counter to keep in sync.

## Consequences
- A refund/cancellation reversal is a `status` write (`→ REVERSED` or `→ CANCELLED`) plus a history row — not a new offsetting ledger entry. The actual wallet-balance correction this implies (Q-07: "wallet never goes negative... shortfall recovered from future earnings") is explicitly a future wallet-phase concern, the same boundary Phase 5 already drew around payment-gateway capture — this phase makes the commission's status reversal correct and auditable; crediting/debiting an actual wallet balance is out of scope until that phase exists.
- `Commission.orderItemId` is nullable and left unset in this phase's actual calculation (commissions are computed per matching-kind item group, not per individual order line) — present in the schema for forward compatibility if a future rule needs per-item precision, per the brief's "order item where applicable."
- Mixed-kind orders are correctly handled (each kind's rule, if any, is evaluated against that kind's own subtotal) rather than left as a documented gap.
- Rates/percentages are stored as integer basis points (percent×100), not `numeric`, continuing the same discipline [ADR-0013](0013-commerce-money-math.md) established for coupon/GST/platform-fee rates — never floats, never Decimal, in any money-adjacent calculation in this codebase.

## Alternatives considered
- **True insert-only event log per status change** (one row per lifecycle step, current state = latest row) — rejected for this phase as unjustified complexity: no consumer yet needs to replay the ledger to derive a balance, and it would be a bigger deviation from the `Order`/`OrderStatusHistory` pattern this codebase already has a tested precedent for. Revisit if/when a wallet-balance read genuinely needs ledger-replay semantics.
- **Whole-order calculation base regardless of item kind** — rejected: silently wrong the moment a cart mixes kinds from the same vendor, which Phase 5's cart model explicitly allows.
- **A separate integer `version` counter on `CommissionRule`** — rejected as redundant: the row's own id/`effectiveFrom` already serves as an unambiguous version pointer, and a counter needing separate incrementing logic is one more place to get out of sync with reality.
