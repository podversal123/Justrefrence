# ADR-0015: Wallet race-safety via conditional updates, e-pin keyed-hash lookup, transfer built dormant

## Status
Accepted

## Context
Phase 7 builds the wallet, payout, e-pin, and subscription subsystems against [business-rules.md](../business-rules.md) Q-09–Q-17. Three implementation questions needed resolving:

1. **Race-condition safety for a balance that must never go negative** ([ADR-0002](0002-money-representation.md): `wallets.balance CHECK >= 0`), without `SELECT ... FOR UPDATE` (Prisma has no first-class support for it, and none of this codebase's existing money-safety code uses it — Phase 5's stock-decrement defense set the precedent instead).
2. **E-pins must be looked up directly by the code a member types in at redemption** (there is no other identifier to scope the lookup by), but [security.md](../security.md) requires they be "stored and looked up by hash exactly like passwords" and never logged in the clear. A per-row-salted slow hash (the right choice for a login password) cannot support a direct `WHERE code_hash = ?` lookup, because the same input produces a different hash every time salt differs.
3. **[business-rules.md Q-10](../business-rules.md#q-10-member-to-member-transfers-️-legal)**: member-to-member wallet transfer is explicitly legal-gated — "the transfer endpoint exist[s] in the RBAC/API design but [is] not implemented/enabled until legal review confirms scope," and `wallet:transfer` is already marked "dormant" in [rbac.md](../rbac.md).

## Decision
1. **Every wallet balance mutation is one atomic conditional `UPDATE`** — `prisma.wallet.updateMany({ where: { id, balance: { gte: amount } }, data: { balance: { decrement: amount } } })` for a debit (returns 0 rows affected, not a negative balance, if insufficient funds), and an unconditional increment for a credit (which can never violate the `>= 0` invariant). This is the exact pattern Phase 5 already established and tested for product-stock decrements (`docs/adr/0013-commerce-money-math.md`) — the WHERE clause is re-evaluated against the row Postgres locks for the UPDATE's duration, so two concurrent debits against an insufficient balance can never both succeed. Every mutation also writes an insert-only `WalletTransaction` row with a required, unique `idempotencyKey` inside the same transaction as the balance write, giving both race-safety and idempotency from one mechanism.
2. **E-pin codes are hashed with HMAC-SHA256, keyed by the same server-side secret already used for bank-account-number encryption** (`FIELD_ENCRYPTION_KEY`), not a per-row-salted slow hash. HMAC is deterministic for a given key (so `WHERE code_hash = hmac(code)` is a valid direct lookup) while remaining infeasible to reverse or brute-force without the server-side key even if the `epins` table leaks — the property a salted-slow-hash gives passwords (defense if the *hash itself* leaks) isn't the threat model here, since the code's own entropy (16 random characters from a 32-symbol alphabet) already makes offline guessing impractical; what HMAC adds is that the hash alone, without the key, reveals nothing and cannot be dictionary-attacked for a *specific* code the way a reused/human-chosen password hash could be. A wallet PIN (6 digits, genuinely low entropy, verified against a single already-known wallet row rather than looked up by) uses the opposite tool: a per-wallet-salted `scrypt` hash, the same class of defense a password gets, since brute-forcing a 6-digit space is otherwise trivial if the hash leaks.
3. **`wallet:transfer` is fully modeled (schema, repository function, unit-tested math) but the Server Action returns a clear "not yet enabled — pending legal review" error rather than moving any money.** This is not a stub left unfinished; it is the literal instruction in Q-10 ("exist in the RBAC/API design but are not implemented/enabled") implemented as a deliberate, permanent-until-further-notice gate, the same boundary this codebase has already drawn around live payment-gateway capture (Phase 5) and wallet crediting from commissions (Phase 6, now closed by this phase for the commission→wallet direction only, never for member→member movement).

## Consequences
- No `SELECT ... FOR UPDATE`, no explicit advisory locks, and no new infrastructure — wallet race-safety rides on the same Postgres row-locking behavior already relied on for stock, using a pattern this codebase's own tests can meaningfully exercise (see the "stock race" test precedent and this phase's own concurrent-debit tests).
- `getFieldEncryptionKey()` (Phase 4) now serves two distinct purposes — AES-GCM encryption (bank account number, reversible) and HMAC keying (e-pin codes, one-way) — documented explicitly at each call site so the dual use is never mistaken for one primitive reused incorrectly as the other.
- A member-to-member transfer UI, if ever built on top of the dormant permission, requires no schema change — only removing the Server Action's early-return gate once Q-10's legal review clears it.
- Commission → wallet crediting (Phase 6's `AVAILABLE` status) now actually credits the beneficiary's wallet; a subsequent `REVERSED` (refund after the commission was already credited) attempts a full claw-back debit, and — consistent with Q-07's "wallet never goes negative; shortfall recovered from future earnings" — if the wallet no longer holds enough to claw back in full (e.g. already paid out), this phase debits whatever is currently available down to zero and records the uncovered shortfall plainly in `audit_logs` and the transaction's own ledger row for `FINANCE` to act on manually. Automatic netting of a shortfall against the member's *future* commission credits is not implemented in this phase (not asked for in the Phase 7 brief, and a materially larger feature in its own right) — flagged here rather than silently assumed.

## Alternatives considered
- **`SELECT ... FOR UPDATE` inside an explicit transaction** — rejected: Prisma's query builder has no first-class support for it (would require raw SQL at every balance-mutating call site), and the conditional-`UPDATE` pattern already gives the identical race-safety guarantee with code this codebase already has a tested, understood precedent for.
- **Per-row-salted slow hash for e-pin codes, with a secondary non-secret lookup column** (e.g. storing a separate, shorter non-salted prefix hash to narrow the candidate set before verifying) — rejected as needless complexity: entropy of a 16-character random code is already far outside brute-force range, so a deterministic keyed hash gives a strict single-query lookup with no meaningful security trade-off over the more complex two-phase scheme.
- **Building member-to-member transfer fully, flagged off by a runtime config switch** — rejected: a switch that's trivial to flip without re-reading Q-10's legal caveat is a worse safeguard than a code path that doesn't move money at all; the Server Action's hardcoded refusal is the harder-to-accidentally-bypass version of the same intent.
